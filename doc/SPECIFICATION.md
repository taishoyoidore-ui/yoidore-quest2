# 大正酔いどれクエスト - システム基本設計・機能仕様書

## 1. 概要と目的

### 1.1 プロジェクト概要
「大正酔いどれクエスト」は、大正区内の飲食店を巡る街ぶら・はしご酒イベント「大正酔いどれクエスト」の公式ガイド＆参加型クエストWebアプリです。

第1回イベントで好評だった「紙の冒険の書（台紙）」に店主が手書きサインを書くという**アナログな交流体験・接客負荷軽減**を軸とし、**LINE公式アカウントと連動したデジタル機能（マイルストーン達成QR解除・オンデマンド酒場クーポン・店頭消し込み）**を組み合わせた**「ハイブリッド運用モデル」**を採用しています。

### 1.2 主な目的とハイブリッド運用の背景
1. **店舗接客負荷の完全解消と偽造防止**: 全参加酒場での会計時個別QRスキャンを廃止し、紙の冒険の書（手書きサイン）で周遊。運営店（バックオフィスで `is_organizer: true` に指定された店舗）のみで達成軒数確認とQRスキャンを行うことで、参加店舗のオペレーション混乱を防止。
2. **LINE公式アカウントの友達獲得とエンゲージメント強化**: 参加導線をLINE公式アカウントに一本化。過去回次の友だち全員をそのまま引き継ぎ可能。
3. **カスケード特典付与（まとめ獲得）**: 参加者が上位のマイルストーン達成QR（例: 10軒達成QR）をスキャンした際、未獲得の下位特典（5軒達成分等）も自動で合算付与され、取りこぼしなく獲得可能。
4. **オンデマンド酒場クーポン方式（回数券チケット）＆直感的な一体型UI**: 獲得したクーポン利用可能枠（例: 5回分）は、イベント終了後のクーポン利用期間に来店時にその都度1店舗ずつ選んで消し込みを行う回数券チケット方式。冒険の書内で「獲得特典カード・クーポン利用可能期間・残枠・利用履歴」を一元管理。
5. **クーポン操作の一本化と店舗詳細での誤解防止**: 本開催期間中に店舗詳細で「クーポン」が表示されることによる「今すぐ使える」との誤解や会計時の店舗質問トラブルを防止するため、店舗詳細からはクーポンUI・ボタンを撤去。クーポン確認・利用操作は「冒険の書」画面に完全一本化。
6. **フェーズに応じたクーポン利用制御と動的期間明記**: 本開催中（サイン集め期間）はクーポンの消し込みをロックし、イベント終了翌日〜有効期限までの期間に対象店舗全店で使える運用を確立。UI上では「後夜祭」などの分かりにくい呼称を避け、「📅 利用可能期間: M/D(曜日) 〜 M/D(曜日)」「【イベント終了後に利用可能】」と動的日付に基づき明記。
7. **確実な店頭消し込み**: 特典利用時に店舗スタッフがスマホ画面上でスライド消し込み操作を実行し、規定回数の使い切りで特典コンプリート。二重利用を防止。
8. **安全な並行運用アーキテクチャ**: 9月末まで稼働している現行イベント・クーポンを一切阻害せず、同じLINEプロバイダー内で完全に共存・切り替え可能な設計。
9. **シーズン制（回次管理）アーキテクチャ**: 第2回、第3回、第4回…とソースコードの再構築なしにバックオフィスからワンクリックで開催回を切り替えられる設計。
10. **バックオフィス運営管理システム**: 特典ランク（5軒・10軒・15軒達成等）に応じた運営店専用卓上POP・QRコードの自動生成・A4印刷、ユーザー/クーポン管理・CSV出力を完備。

### 2.1 友だち限定セーフティガード (LINE Friendship Gate) 仕様

1. **アクセス制限と目的**:
   - 本アプリはLINE公式アカウントの友だち限定で利用可能な設計となっており、外部Webリンクや直接URL共有によって「友だち追加していないユーザー」や「公式アカウントをブロック中のユーザー」がアプリを操作することを防止します。
2. **LINE友だち状態の動的検証 (`liff.getFriendship()`)**:
   - アプリ起動時のLIFF認証（`initAuth()`）において、LINE SDKの `window.liff.getFriendship()` を実行し、公式アカウントの友だち追加フラグ（`friendFlag: boolean`）を取得・検証します。
   - `friendFlag === false`（未追加またはブロック中）と判定された場合、アプリ全体の操作を停止し、RPG風「🔒 友だち登録が必要です」全画面セーフティオーバーレイを表示します。
3. **ユーザー体験と復旧導線**:
   - セーフティオーバーレイ上からワンタップで公式アカウントの友だち追加画面（`https://line.me/R/ti/p/@277lqewi`）へ遷移可能。
   - 友だち追加完了後、「🔄 友だち追加したので再読み込み」ボタンをタップすることで即座にロックが解除され、ゲームを開始できます。
4. **開発・ローカル環境の互換性**:
   - LIFF環境外（PCブラウザローカル開発環境やバックオフィス管理画面）では、自動的にフレンドチェックをバイパス（`isFriend = true`）し、デバッグや管理業務を阻害しません。

## 4. データベース設計と物理運用アーキテクチャ (Supabase / PostgreSQL)

> [!IMPORTANT]
> **【AI・開発者向け 最重要アーキテクチャ・ガードレール（設計不変原則）】**
> 本システムは、サーバーレス/フロントエンド完結（SPA）におけるSupabase RLS権限トラブルの防止および原子的（アトミック）な設定同期を実現するため、**「設定ドキュメント（NoSQL型）ハイブリッド構造」** を採用して本番稼働しています。
> 1. **独自判断による設計・テーブル変更の絶対禁止**:
>    AIや実装者が独断で新しいテーブルを作成したり、`__system_config__` の読み書き先を別の物理テーブルへ切り替える等の設計変更を行ってはならない。必ず設計者（ユーザー）の明示的な指示に従うこと。
> 2. **稼働テーブルの厳守**:
>    実際に稼働している物理テーブルは **`users`, `stores`, `visits`, `user_coupons` の4つのみ** である。
> 3. **手動SQL実行時の設定レコード保護**:
>    テストデータ削除等で `users` テーブルを操作する際は、必ず `WHERE line_user_id != '__system_config__'` を付与し、システム設定レコードの巻き込み削除を絶対に防ぐこと。

### 6.1.2 特定日限定営業店舗（1日のみ営業等）の運用規則と全店制覇算定ルール

> [!NOTE]
> **【ステータス: 運営メンバー検討中（保留中）】**  
> 本項の「特定日営業店舗を除外した全店制覇仕様」は、現在運営チーム内で合意形成中の提案仕様です。現行のコードおよびDBはまだ変更されていません。  
> 検討完了・合意後に、どのAI/開発者でも迷わず即座に安全・正確に実装できるよう、UI表示案・計算式・コード差分等をまとめた設計書 [PROPOSAL_all_stores_conquest_special_date.md](file:///C:/AG_WORK/yoidore-quest2/doc/PROPOSAL_all_stores_conquest_special_date.md) を策定済みです。

イベント期間中、極めて限定された日時（例: 期間中1日のみ・数時間のみ等）に限り営業を行う店舗（特定日限定営業店舗）が存在する場合があります。一般参加者が全店制覇（最高位特典マイルストーン）を目指すにあたり、特定日営業の参加可否によって達成不能や客足集中・売り切れクレーム等の現場トラブルが生じないよう、以下の**設計・運用ルール**を定めます。

#### ① 特定日限定営業店舗のデータ管理
- **特定日フラグ**: 各シーズンの店舗データ内 `special_date` に営業日（ISO日付形式: `YYYY-MM-DD`）を格納。
- **営業時間**: 各シーズンの店舗データ内 `quest_hours` に営業時間を格納。
- ※（参考）第2回実績値: `special_date = '2027-01-30'`, `quest_hours = '11:30〜15:30'`（店舗ID: `store-45`）。

#### ② 全店制覇特典（最高位マイルストーン）における必須除外ルール
1. **全店制覇の必要来店数（`required_visits`）の自動算出式**:
   - バックオフィスで特典マイルストーンの「👑 全軒制覇（全店舗達成）」を選択して保存する際、単に全参加店舗数を充てるのではなく、**「今期参加店舗数 − 特定日限定営業店舗（special_date設定あり）数」** を自動算出して登録する。
   - 計算式: $\text{required\_visits} = \text{参加店舗数} - \text{特定日営業店舗数}$
   - これにより、特定日営業の店舗に足を運ぶことができない参加者であっても、他の参加店舗を巡ることで**確実に「全店制覇」を達成可能**とする。
2. **特定日営業店舗に来店した場合の扱い（通常カウント）**:
   - 特定日営業店舗への来店も、正規のハシゴ軒数（`visits`）として1軒分カウントされる。
   - 他の店舗を1軒スキップしても、特定日店舗を訪れていれば所定軒数で全店制覇を達成できる（救済・代替店舗として機能する）。
3. **アプリ判定ロジックの不変原則（リアルタイム引き算の禁止）**:
   - アプリ側の判定は常に `visitedCount >= tier.required_visits` の単一絶対評価を維持する。
   - アプリ実行時に特定日店舗の有無を動的に差し引くような複雑な条件分岐は行わず、DBに保存された `required_visits` を唯一の真実（Single Source of Truth）として判定する。

#### ③ 画面表示・ユーザー周知仕様
1. **酒場一覧カード ＆ 店舗詳細モーダル**:
   - 特定日設定（`special_date`）がある店舗には、事実のみを淡々と補足する。
   > `※営業日時の都合上、本店舗へのご来店がなくても「全店制覇」を達成可能です。ご来店時は通常通りハシゴ件数（1軒）に加算されます。`
2. **冒険の書「全店制覇」宝箱カード**:
   - 余計な数字や言い訳を書かず、シンプルに達成目標を表示する。
   > `👑 条件: 全店舗達成`

### 6.4 データ型・クレンジング・正規化ルール

1. **提供時間（`hours`）**:
   - Excel内部の小数シリアル値（例: `0.5`, `0.625`, `0.708`）やTime型を判定し、`HH:mm〜HH:mm` 形式（例: `15:00〜22:30`, `12:00〜00:00`）へ自動変換。
2. **提供曜日（`days`）**:
   - `全て` ➔ `月,火,水,木,金,土,日`
   - 「月曜日」「火曜日」等の「曜日」の「日」に誤爆しないよう正規表現（`/日曜日|日曜/`）で厳密に判定し、`月,火,水,木,金,土` 形式に正規化。
3. **価格・料金（`set_price`, `quest_price`）**:
   - `500円〜900円` などの価格幅表記や `男性2000円　女性1500円`、`無料` 等の柔軟な記述に対応するため、**文字列（`string`）を許容**。アンケートExcelの値を生の文字列のまま欠落なくインポートし、バックオフィスで自由に修正・調整可能な運用設計とする。アプリ表示時は純粋な数値なら `¥1,000 (税込)`、文字列・範囲なら `500円〜900円 (税込)` と自動判別整形。
4. **チャージ料・限定数量（`set_charge`, `set_limit` 等）**:
   - `None` や空文字は `不要` または `""` にクレンジングし、酒場の自由記述（例: `酔いどれセットの方は０円`, `おばんざいが無くなるまで。`）をそのまま尊重して保持。
5. **スタイル（`style`）**:
   - `テールブあり` などの誤字補正を行いながら、`カウンターメイン、テーブル1席あり` などの詳細記述をそのまま維持。
6. **既存マスタ情報保護（写真・ロゴ・地図URL・キャッチコピー）**:
   - アンケートExcelに含まれないシステム管理項目（`photo_url`, `logo_url`, `map_url`, `insta_url`, `catchphrase`）は、インポート時に既存マスタ（DB）の値を自動継承し、空文字上書きを防止。

### 6.6 バックオフィス店舗入力・編集画面（admin.html）の連携仕様

1. **席スタイル（`style`）の自由記述対応**:
   - 既定選択肢（`テーブルあり`, `カウンター`, `立ち飲み`, `テイクアウト専門`）に加え、`その他 (直接入力)` をサポート。
   - アンケートで自由入力された詳細（例: `カウンターメイン、テーブル1席あり`）を丸めずに保持・編集可能とする。
2. **参加企画（`plan_type`）の選択**:
   - `「酔いどれセット」・「お遊びゲーム」両方で参加` / `「酔いどれセット」のみで参加` / `「お遊びゲーム」のみで参加` のプルダウン選択（既存データの「店舗クエスト」表記とも完全互換）。
3. **新規シーズン作成時の店舗データ初期化・引継ぎ**:
   - 新規シーズン作成時は、初期状態で全店舗が「未参加」として安全に作成される。
   - アンケートExcelのインポート、または「前シーズンの参加店舗設定を一括コピー」操作により、瞬時に新シーズンの参加店舗マスタを構築可能。
4. **決済方法（`payment`）の双方向同期**:
   - チェックボックス（現金/カード/PayPay等）と、「その他決済」テキスト欄を組み合わせて自由記述（QR決済の種類等）を漏れなく保持。
5. **店舗情報の確実な保存・即時反映（CRUD安定化）**:
   - 既存店舗の編集保存時は、選択中シーズンに対応する `season_stores` と基本マスタ `stores` の双方へ安全に保存を実行。

## 9. データ取得・フォールバック偽装の完全禁止規約 (Strict Data Integrity Policy)

本システム（ユーザーアプリ、バックオフィス管理画面、API通信層の全領域）において、**データ欠損・未定義時にコード内の固定値（ダミー文字列・仮データ）を代入・フォールバック表示して正常に見せかける実装を恒久的に全面禁止**とします。

### 9.1 禁止事項（Anti-Patterns）
1. **未定義プロパティに対する固定文字列・固定値の暗黙補填の禁止**:
   - `newHero?.title || '初陣'`、`newHero?.level || 2`、`season.name || '大正酔いどれクエスト'` のように、プロパティが存在しない・取得できない場合にコード内の固定値をフォールバック代入する処理の禁止。
2. **新規作成・入力ダイアログにおける固定値・決め打ち文字列の自動初期セット禁止**:
   - 新規作成モーダル（特典ランク、店舗マスター、シーズン開催設定等）の入力欄（`<input>` や `<select>`）に、あらかじめ固定のタイトル、数値、エリア、カテゴリ、営業情報等を初期値（`.value`）として強制プリセットする処理の禁止。
   - 入力例・ガイダンスは必ず HTML の `placeholder` 属性（例: `placeholder="例: 5軒ハシゴ達成特典"`）またはヘルプテキストで提示し、実際の入力値は完全な空文字（`""`）または未選択状態（`value=""`）で開くこと。
3. **引数不整合やデータ欠損の隠蔽の禁止**:
   - 呼び出し側の引数エラーやオブジェクト構造の不整合が発生した際、デフォルト値で画面を成立させてバグを正常に見せかける処理の禁止。
4. **データベース設定に存在しないダミーマスタのハードコード禁止**:
   - データベース（Supabase）上に登録されていない店舗情報、特典ランク、勇者称号、ガイダンス・心得、シーズン設定等をプログラム内に固定値として埋め込み、それを代替表示する処理の禁止。

### 9.2 遵守すべきデータ設計・実装原則
1. **データベース（Single Source of Truth）の絶対遵守**:
   - すべての称号、特典、店舗、シーズンデータはデータベースを唯一の真実として扱い、DBマスタから取得した実データを厳格に使用する。
2. **新規入力フォームにおけるクリーン初期化とプレースホルダー活用**:
   - 新規作成時のフォーム入力欄は一切の決め打ち初期値を排し、空文字・未選択で初期化する。利用者の入力負担軽減・誘導は `placeholder` の例示または入力バリデーションによって行い、意図しない固定値がそのままDBに登録される事故を根絶する。
3. **データ欠損・未取得時の明示的ハンドリング**:
   - データが存在しない場合は、勝手な仮データを捏造せず、空状態（`[]`）、未設定表記（例: `-` や未設定メッセージ）、または開発・デバッグ環境で即座に検知可能なログ・エラーハンドリングを行う。
4. **引数シグネチャの厳密な型・構造チェック**:
   - コンポーネントやモーダル関数は、期待するオブジェクト構造を明確にし、データ不整合時はフォールバックで誤魔化さず根本原因を即座に特定・修正できる構造を維持する。
